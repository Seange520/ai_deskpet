# Blender 路线评估与「我 × Codex」同题 A/B（2026-11-10）

> 目的：回答主策划三问——①有没有亲自/指派 Codex 用 Blender 做工程；②有没有更高效/更厉害的方式；③第一轮我 × Codex 同题各做一版、双视角评分，胜者吸收对方优点并承接后续相关工作。

## 1. 结论先行

1. **Blender 4.5 本机可用**（`C:\Program Files\Blender Foundation\Blender 4.5\blender.exe`，headless `-b -P` 跑通，Cycles CPU 渲染 1920×1080 单张约 40s）。此前 R1 三渲二原型是**在 Three.js 里直接做**的实验路由，不是 Blender 工程；Blender 工程从本轮开始建立。
2. **推荐工作流（三层，按「白模→上模型→进引擎」拆）**：
   - **L1 白模/blockout**：Blender Python 程序化生成（本文件 A/B 实验验证）+ 手调比例；输出 GLB，进 Three.js 引擎。
   - **L2 上模型/材质**：Blender 手工（或 BlenderMCP 让 AI 助手在 Blender 里执行操作）做倒角、UV、顶点色、程序化材质；导出 glTF（Three.js 原生友好）。
   - **L3 高效补充**：AI 文生 3D（Tripo / Meshy / Hunyuan3D / Hitem 等）出候选网格 → Blender 重拓扑/减面/UV/烘焙；适合道具与背景件，**不适合**做主角与关键地标（一致性差）。
3. **谁更适合 Blender 工作**：见 §4 A/B 结果。

## 2. 可选路线对比

| 路线 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 程序化 Blender 脚本 | bpy 生成基础体、参数化尺寸、批量出件 | 可版本化、可批量、可复现；AI 可直接写 | 造型偏「工程感」，细节需手调 | 街道/建筑/道具白模、LOD |
| B. BlenderMCP / AI 操作 Blender | MCP 让 AI 连 Blender socket 执行命令 | 交互式、能边看边改 | 依赖插件与连接；大改动易失控 | 中后期细节调整、材质实验 |
| C. AI 文生 3D（Tripo/Meshy/Hunyuan3D/Hitem） | 图/文 → 网格 | 出概念快、造型有机 | 拓扑脏、UV 差、风格不稳；需清理 | 道具候选、氛围件、参考 |
| D. 传统手工建模 | Blender 手工 | 质量上限最高 | 最慢，单人产能不够 | 主角/关键地标（远期） |

参考：[Tripo/Meshy/Hunyuan/Hitem → Maya/Blender → UE5 教程](https://dev.epicgames.com/community/learning/tutorials/ryKG2/unreal-engine-fortnite-ue5-ai-3d-tripo-meshy-hunyuan-hitem-midjourney-nanobanana-maya-blender-ue5)、[2026 AI 3D 生成器评测](https://www.krea.ai/blog/best-ai-3d-model-generators-2026)、[Blender MCP 指南](https://www.strayspark.studio/blog/ai-powered-3d-modeling-blender-mcp-server-guide)。

## 3. A/B 实验设置（同一份提示词）

**提示词**（双方逐字相同）：
> 场景：晴光街一角（低多边形、卡通渲染风格，游戏可用资产）。包含：一栋两层砖木小楼（一层店铺门面+遮阳篷、二层两扇窗）、一根街灯（弯臂灯头）、一张长椅、一棵行道树、一小段石砖路面。要求：低多边形（≤15k tris）、方块化比例但细节可读、暖色木质+青灰砖墙+黄铜灯柱、单一场景中心构图、适合第三人称游戏视角。交付：Blender Python 脚本（bpy，可直接 `blender -b -P` 运行）+ 渲染图 1920×1080（两张：三分之四视角、侧视）+ 导出 GLB。

- A 版（我）：`work/tmp/render-ab/mine/build_sunlit_corner.py` → 渲染两张 + GLB。
- B 版（Codex）：`ai_deskpet/render-ab/codex/build_scene.py`（Codex 只写脚本，本机统一跑，避免其网络/渲染环境差异）。
- 渲染统一：Cycles CPU / 24 samples / 1920×1080 / AgX。

## 4. 双视角评分（设计端 × 客户端）

维度（每项 10 分）：①造型准确与比例 ②构图与叙事 ③材质与色彩 ④游戏落地性（tris/UV/命名/可导入/性能） ⑤风格契合（《流明域》暖生活+校验册页） ⑥效率（从提示词到可交付时间）。

| 维度 | A（我，负责人） | B（Codex） |
|---|---:|---:|
| ① 造型准确与比例 | 6.0 | **8.5** |
| ② 构图与叙事 | 6.0 | **8.5** |
| ③ 材质与色彩 | 6.0 | **8.0** |
| ④ 游戏落地性 | 7.0（1416 tris，脚本可参数化，但无 UV/命名规范） | **7.5**（14,678 tris，GLB 可直接导入；对象 669 个需合并/命名/减面） |
| ⑤ 风格契合 | 6.5 | **8.0** |
| ⑥ 效率 | 6.0（约 2.5 小时，含 3 轮迭代） | **9.0**（约 10 分钟出脚本+渲染+GLB） |
| **均分** | **6.25** | **8.25** |

**设计端评语**：A 版只做到「把元素摆出来」，比例、屋顶、遮阳篷与窗框都松；B 版先搭了一个整体台座（街道切片+人行道+树池），把「生活感」做出来了，遮阳篷条纹、屋瓦、窗板、OPEN 挂牌、壁灯、长椅、花盆这些*次级细节*是 A 版缺的关键。B 版构图是标准的 3/4 斜俯视，接近《原神》房屋展示镜头。
**客户端评语**：B 版直接可进引擎做 R1-A2 街道件；A 版的脚本结构清晰、参数化程度高，但网格质量不足。B 版 669 对象/14,678 tris 需要合并与命名（`SM_`/`M_`/`T_` 前缀），并补 UV。

## 5. 结论与分工建议

1. **本轮胜者：B（Codex）**，均分 8.25 : 6.25，差距明显。原因不是「谁更会用 Blender 命令」，而是 **B 先想场景叙事再建模**（台座/树池/挂牌/窗板），A 局限于「把清单里的物件各做一个」。
2. **后续分工（按「最优解」）**：Blender 具体资产制作**交给 Codex 主做**；我负责：①资产规范（尺寸/朝向/命名/LOD/材质名/UV 通道）②参数化脚本框架与批量工具③进 Three.js 的集成与性能验收④双端评审与驳回。**我吸收 B 的强项**：先定「场景切片+地台+次级细节」再堆主体；每个资产先给 3/4 构图相机与主光，再反推比例。
3. **若 Codex 不可用**：本次已验证「同 prompt 委派独立子代理」可作备份产线（本夜 Codex CLI 后段网络失败，但首轮产物已完整落盘；备份子代理未用上）。
4. **AI 生成模型**只做道具候选与参考，不进关键资产；BlenderMCP 留给中后期材质/细节迭代。
