# 双端审核协议 V1（设计端 × 客户端）

> 主策划指令（2026-11-10 03:00）：「所有流程都需要设计端加客户端视角双重审核。」
> 适用：UI/美术/渲染/玩法/教学/小说/发行包，一切对外可见物。

## 一、两个视角

### A. 设计端（Design Review）
回答「它是否服务核心体验」：
1. 核心体验对齐：这条内容服务哪个玩法/叙事/教学目标？删掉会不会更好？
2. 风格一致性：与《第七校验·流明域》的纸/墨/黄铜/自然光/生活质感是否同源？
3. 结构可扩展：能否被后续章节、联机、PVP、DLC 复用而不返工？
4. 正典与教学正确性：与 CANON_DECISIONS（A1–A22）、教学大纲、知识图谱是否冲突。
5. 成本与产能：单人+AI+Codex 能否在预算内完成；是否引入不可维护依赖。
6. 合规与红线：不卖战力/答案/抽卡数值、无真实充值（内部版）、素材原创、无侵权。

### B. 客户端（Player Review）
回答「玩家第一次接触会不会留下」：
1. 前 30 秒：看得懂在干什么吗？下一步明确吗？
2. 可读性：字号/对比度/信息密度/层级；1080p 与 390px 手机各看一次。
3. 情绪与爽感：有没有一个「值得截图/分享」的瞬间？失败是否可理解？
4. 操作负担：要点几次、要记几个键、误触后果。
5. 性能体感：首屏、切换、掉帧、发热（桌面/移动各记一次）。
6. 信任与诚实：是否像宣传的那样能玩；有没有「看起来能玩其实不能」。

## 二、流程

1. 交付物进入 `work/acceptance/<批次>/`（截图 + 指标 + 复现脚本）。
2. 设计端先审：写 verdict（通过/有条件通过/不通过）+ P0/P1。
3. 客户端再审：同一份材料，只从玩家视角写；允许与设计端结论不同。
4. 合成结论：两条都通过或有条件通过（P0 清零）才入库；不通过则回炉，记录原因。
5. 每次审核留档：`work/handoff/review/DUAL_REVIEW_<date>.md`。
6. P0 未清零不得对外（商店页/预告片/试玩包/推送）。

## 三、判定口径

- **通过**：双端均「通过」。
- **有条件通过**：双端均无「不通过」，且 P0 有明确修复计划与截止时间。
- **不通过**：任一端判定不通过，或 P0 涉及欺骗/侵权/安全。
